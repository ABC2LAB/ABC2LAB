## GitHub 관리자의 최초 설정 체크리스트

- [ ]  표준 OS·CPU·Python 기준과 최초 검증할 uv 버전을 README에 기록한다.
- [ ]  루트 `.python-version`, `.gitignore`, `requirements.txt`를 작성한다.
- [ ]  아래 8개 모듈 폴더와 각각의 초기 `requirements.txt`를 준비한다. 사용 라이브러리가 미정인 모듈 파일은 설명 주석만 두어도 된다.
- [ ]  초기 공통 패키지와 이미 필요한 모듈 패키지를 함께 해결하여 `requirements.lock.txt`를 생성한다. 패키지 이름만 있는 빈 기준으로 출발하지 않는다.
- [ ]  README에 최초 설치·업데이트 후 동기화·테스트 명령과 환경 확인 방법을 적는다.
- [ ]  새 clone과 새 `.venv`에서 Python 버전, 잠금 파일 설치, 의존성 검사, 초기 선정 패키지 import가 성공하는지 확인한다.
- [ ]  검사한 main 커밋·Python/uv 버전·확인 결과를 README에 남기고 초기 기준 커밋을 main에 올린다. 개발 시작 기준 커밋은 명세의 문서 버전과 별도로 관리한다.
- [ ]  모듈 담당자와 GitHub 계정을 매핑하고 PR로 병합하도록 운영한다. main 보호·필수 검사·CODEOWNERS 사용 여부는 저장소의 지원 기능에 맞춰 설정하고 적용 상태를 기록한다.
- [ ]  각 팀원이 같은 커밋에서 설치를 재현하고 환경 버전을 확인한 뒤 담당 모듈 개발을 시작한다.

현재 체크는 실제 GitHub 작업을 수행한 사람이 완료한다. 이 문서를 정리했다는 이유로 설정 완료·설치 성공·필수 검사 설정을 완료 처리하지 않는다.

## 팀원의 clone 후 시작 순서

1. 관리자가 공개한 초기 기준 main 커밋을 clone하고 표준 Ubuntu/WSL 터미널에서 저장소 루트로 이동한다.
2. README에 지정한 uv 버전을 설치한다. `.python-version`의 Python을 설치하고 저장소 루트 `.venv`를 만든다.
3. **루트 잠금 파일을 동기화**한다. 모듈별 requirements만 따로 설치한 환경을 팀의 검증 기준으로 사용하지 않는다.
4. 실제 Python 경로·버전과 패키지 호환을 확인하고, 필요한 자기 모듈의 로컬 환경변수를 준비한다.
5. 자기 모듈 README의 실행·테스트 명령으로 개발한다. 표준 환경에 없는 의존성은 변경 절차로 제안한다.

### 최초 설치 명령 — 표준 Linux/WSL 환경

```bash
uv --version
uv python install
uv venv .venv
uv pip sync --python .venv/bin/python --require-hashes requirements.lock.txt
uv pip check --python .venv/bin/python
.venv/bin/python -c 'import sys; print(sys.version); print(sys.executable)'
```

명령은 루트 설정 파일과 해시를 포함한 잠금 파일이 준비된 뒤 사용한다. `.python-version`은 버전 선택 기준이며 파일을 clone하는 것만으로 Python이 설치되지는 않는다.

### pull 후 의존성이 갱신되었을 때

```bash
git pull
uv pip sync --python .venv/bin/python --require-hashes requirements.lock.txt
uv pip check --python .venv/bin/python
```

Python 버전 자체가 바뀌면 README의 변경 안내에 따라 지정 Python을 설치하고 해당 버전으로 `.venv`를 다시 준비한다. 코드 실행은 `.venv/bin/python` 또는 같은 인터프리터를 선택한 IDE에서 수행한다.

## 모듈 담당자가 끝까지 책임질 범위

1. 자기 입력 Schema·지원 버전·ID·참조·해시를 검증한다.
2. 계약이 허용한 값·개수·빈 배열·null·partial을 처리하고 잘못된 입력을 표준 실패로 기록한다.
3. 내부 처리 후 합의한 출력 Schema·필드 의미·근거 대응을 검증한다.
4. 자기 소유 경로에 결과를 저장하고 실제 성공·실패·생성 경로를 공개 호출 규약으로 알린다.
5. 정상·부분·실패·입력 변화·외부 의존성 실패를 자기 테스트와 fixture로 확인한다.
6. 공통 잠금 환경에서 독립 실행·테스트 결과를 README/PR에 기록한다. 별도 통합 담당이 코드를 맞춰주는 작업을 전제로 하지 않는다.

다른 모듈의 내부 코드·utils·Schema·전역 가변 상태를 import하거나 직접 수정하지 않는다. 외부 입력 파일·근거·명세된 세션/KG 창구만 읽거나 사용한다. 생산자·소비자 표와 실패 처리는 [공통 계약 · 파일 형식과 전달 규칙](02-common-contract.md)을 따른다.

## 결합도를 최소화하는 개발·완료 기준

- 모듈 간 의존은 명세된 입력·출력과 꼭 필요한 공개 창구로 한정한다. 내부 코드·클래스·utils·Schema·DB driver·브라우저 객체·가변 상태를 공유하지 않는다.
- 공개 입력을 자기 내부 모델로 바꾸는 adapter와 외부 창구의 client/대역은 소비자 모듈이 자기 폴더에 둔다. 제공자의 내부 타입이나 구현 파일을 import하지 않는다.
- 파이프라인은 공개 entrypoint의 실행 순서·인자·경로·완료/실패만 연결한다. 모듈이 다른 모듈의 service를 호출하거나 다음 단계를 실행하지 않는다.
- 세션의 생성·갱신·종료는 collector, DB 접속·Cypher·revision 갱신은 knowledge_graph가 소유한다. 다른 모듈은 합의된 창구로 사용하고 내부 상태를 직접 읽거나 수정하지 않는다.
- 공개 창구의 요청·반환 값/타입·오류·버전·만료/반납 규칙은 제공자와 직접 소비자가 해당 연결 구현 전에 확정한다. 아직 합의하지 않은 세부 규약을 각자 추측하여 구현하지 않는다.
- 입력·출력 계약과 의존성이 유지되는 내부 변경은 해당 모듈 안에서 끝나야 한다. 공통 잠금 환경의 패키지 변경은 관리자 전체 호환 검증을 계속 적용한다.

### 독립성 완료 체크

- [ ]  다른 모듈 소스를 실행 경로에서 제외해도 자기 입력 fixture와 공개 창구 대역으로 정상·부분·실패 테스트를 실행할 수 있다. 공통 Python·잠금 환경은 그대로 사용한다.
- [ ]  자기 모듈을 독립 실행하는 명령·필요한 입력/설정·결과를 자기 README에 기록한다.
- [ ]  다른 모듈의 코드·Schema를 import/참조하거나 DB·세션·전역 가변 상태를 직접 공유하는 구현이 없다.
- [ ]  공개 계약과 의존성을 유지한 내부 변경에 다른 모듈 코드 수정이 필요하지 않다.
- [ ]  실제 연결 검증에서는 제공자가 발행한 샘플을 소비자의 자기 입력 검증으로 확인한다. 세션/KG의 오류·만료·revision 대응도 해당 담당자끼리 확인한다.

이 체크는 구현 결과로 완료한다. 문서에 경계를 정한 것만으로 코드의 독립성·실제 연결 검증이 완료되었다고 표시하지 않는다.

## 변경 종류별 협의와 수정 경계

| 변경 | 협의 대상 | 각자 수정·검증할 부분 |
| --- | --- | --- |
| 내부 알고리즘·프롬프트·캐시·배치·자료구조 | 해당 모듈 담당자 | 공개 입출력과 의존성 기준이 유지되면 자기 폴더의 코드·테스트만 변경한다. |
| JSON 필드·타입·enum·단위·필드 의미·버전 | 출력 생산자 + 해당 파일의 모든 직접 소비자 | 생산자는 출력, 소비자는 입력 Schema·adapter·fixture·README를 수정하고 실제 샘플을 함께 검증한다. |
| 의존성 추가·라이브러리 버전 변경 | 제안 모듈 담당자 + GitHub 관리자 + 영향받는 모듈 담당자 | 제안자는 자기 requirements를, 관리자는 전체 lock을 갱신한다. 같은 라이브러리와 하위 의존성을 쓰는 모듈까지 공통 환경에서 확인한다. |
| Python·개발 OS·환경 도구 버전 변경 | GitHub 관리자 + 전체 모듈 담당자 | 관리자가 기준·설치 안내·lock을 갱신하고 각 담당자가 새 환경에서 자기 모듈을 검증한다. |
| 실행 순서·공개 호출·세션/KG 창구 변경 | 제공자 + 직접 호출자/소비자 + 루트 연결 변경 시 관리자 | 제공자가 자기 공개 창구와 문서를, 소비자가 자기 호출·검증을 수정한다. 관리자는 필요한 최소 경로·호출 연결을 반영한다. |
| 정답·테스트 웹·데이터셋 초기 상태 변경 | 평가 자료 담당자 + reporter 담당자 | 자료·버전·초기 상태를 갱신하고 reporter가 자기 개발 평가 입력·결과를 확인한다. |

**JSON 변경과 의존성 변경은 협의 범위가 다르다.** A의 출력 변경에 B가 입력을 맞추더라도 B의 출력이 유지되면 C의 계약을 바꾸지 않는다. 라이브러리 변경은 공유하는 패키지 조합 때문에 다른 모듈에 영향을 줄 수 있어 전체 환경 검사에 포함한다.

### 의존성 변경 절차

1. 모듈 담당자가 사용 이유·직접 의존성·지원 버전을 자기 requirements와 PR에 제안한다.
2. 관리자가 최신 main과 PR의 선언을 함께 해결해 후보 잠금 파일을 만든다. 버전 충돌이 있으면 해당 담당자들과 지원 버전을 조정한다.
3. 담당자가 후보 잠금 환경에서 자기 모듈을 확인한다. 버전이 바뀐 패키지에 영향받는 기존 모듈의 테스트도 같은 환경에서 확인한다.
4. 관리자 전용 루트 변경은 관리자가 반영한다. 모듈 선언·코드와 그에 맞는 잠금 파일이 같은 검증된 병합본에 포함되도록 한다.
5. 병합 후 모든 담당자가 pull하고 공통 잠금 파일로 환경을 동기화한다. 변경 내용을 최종 빌드까지 미루지 않는다.

### 관리자 잠금 파일 생성·검사 명령

```bash
uv pip compile --python .venv/bin/python --generate-hashes requirements.txt -o requirements.lock.txt
uv pip sync --python .venv/bin/python --require-hashes requirements.lock.txt
uv pip check --python .venv/bin/python
```

관리자는 표준 개발 환경에서 생성하고 프로젝트 테스트 결과를 함께 확인한다. 잠금 파일 생성·패키지 호환 검사 성공만으로 기능 동작을 완료 처리하지 않는다.

## 브랜치·PR·병합 규칙

- 모듈 담당자는 자기 작업 브랜치에서 `modules/<module_id>/**`를 수정한다. 다른 모듈·루트 관리 파일 변경은 해당 책임자에게 별도 요청한다.
- PR에는 변경 목적, 입력/출력 계약 영향, 의존성 영향, 사용한 main 기준 커밋·잠금 파일, 실행·테스트 결과를 적는다.
- 일반 구현 PR은 공통 환경에서 자기 모듈의 정상/부분/실패·입력/출력 테스트를 통과한다.
- 계약 변경 PR은 생산자·모든 직접 소비자의 합의와 실제 출력 샘플 수신 검증까지 확인한다.
- 의존성 변경 PR은 전체 의존성 해결과 영향받는 모듈의 공통 환경 검증을 확인한다.
- 실제 모듈이 준비되기 전의 fixture·대역 테스트와 8개 실제 모듈의 전체 실행 결과를 구분해 기록한다.
- 관리자는 병합 순서와 루트 파일을 관리한다. 기능·입출력 검증 실패는 해당 모듈 담당자가 자기 코드에서 해결한다.
- CODEOWNERS는 리뷰 책임을 연결한다. 관리자만 루트 파일을 수정한다는 작업 규칙을 실제 병합에서 강제하려면 지원되는 main 보호·필수 소유자 리뷰 설정을 함께 적용해야 한다.
- Git 충돌이 없다는 보장은 하지 않는다. 자기 폴더 중심의 변경으로 겹침을 줄이고, 잠금 파일 충돌은 최신 선언으로 재생성한 뒤 검증한다.

## 개발 시작과 최종 빌드의 완료 기준

| 단계 | 완료 기준 | 책임 |
| --- | --- | --- |
| 개발 기준 문서 | 모듈 경계·환경·소유권·변경·검증·병합 규칙을 팀이 공유한다. | 이 노션 문서 / 각 역할 |
| 최초 GitHub 설정 | 초기 파일을 main에 올리고 새 clone·새 환경에서 설치·기본 import·의존성 검사를 재현한다. | GitHub 관리자 + 설치 확인하는 팀원 |
| 모듈 완료 | 기준 환경에서 독립 실행·입력 처리·출력 검증·실패 처리와 자기 테스트를 통과한다. | 해당 모듈 담당자 |
| 전체 실행 완료 | 8개 실제 모듈의 합의된 입력/출력과 공개 창구를 연결한 실행이 성공하고 오류·부분 결과도 예상대로 전달된다. | 실패한 연결의 생산자·소비자 / 관리자: 실행본·결과 관리 |
| 최종 배포 | 대상 OS·CPU·Python을 확정하고 검증한 의존성으로 빌드한다. 필요한 Python 패키지·외부 구성요소를 준비해 실제 설치본의 설치·실행을 확인한다. | GitHub 관리자: 배포 구성 / 해당 모듈 담당자: 자원·동작 검증 |

초기 기준은 최소 환경이며 배포 구성은 개발 결과에 따라 갱신한다. 폐쇄망 배포에서는 실제 사용하는 브라우저·Neo4j·로컬 모델·시스템 라이브러리 등 Python 잠금 파일 밖의 자원도 버전·준비 방법을 기록한다. 개발용 테스트 도구와 제품 실행 의존성은 최종 빌드에서 용도를 구분한다.
